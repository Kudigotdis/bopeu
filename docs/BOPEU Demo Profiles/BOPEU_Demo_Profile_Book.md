**Version:** 1.0 · **Prepared:** 25 October 2026 · **Status:** Fictional demo data only

> **Important:** All profile records, names' middle names, identity references, contact details, account references, balances, cases, dependants, submissions and usage metrics are synthetic. The six member display names are retained from the brief, but their associated profile data is invented. Do not import this pack into production, send messages to these contacts, or present synthetic balances/quotes as real member records.

## What is included

- 3 male member profiles and 3 female member profiles, each tied to a different Botswana public-service workplace and region.
- 7 BOPEU staff profiles with separate role permissions and dashboard queues.
- 6 benefit-partner portal users with organization-specific access.
- A benefit directory separating reference-confirmed summaries from offers whose current terms must still be verified.
- 18 demo timeline, noticeboard, document, grievance, application, partner and moderation activities.
- A role-based access matrix to explain how member, staff and partner views differ.

**Product naming note:** the working formal name in the requirements file is *BOPEU Member Services Portal*. *Mmereki* was described as a proposed brand pending approval.

## Client demo walkthrough

1. Open a member's digital card to show a stable demo membership reference, eligibility status, work location and the card's verification token. The token is visual only, not an authentication credential.
2. Compare different benefit states: an active demo savings account, a quote request, a bursary under review and a partner offer whose terms are still pending.
3. Open the sample application tracker to show what a member needs to do next, rather than giving every application the same generic status.
4. Switch staff roles: Marketing can draft posts and manage document-vault metadata; Finance sees check-off exceptions; Welfare sees assigned claims/bursary checklists; Regional Operations sees only assigned regional triage; Legal sees assigned dispute cases; Admin manages accounts, controls and logs.
5. Switch to a partner user and show the narrow eligibility or application response. Partners should not have a member-search screen with access to complete profiles.

## Suggested production schema improvements

- Keep identity, contact, payroll, benefits, dependants, grievances, staff permissions and partner redemptions as separate linked records; never put all sensitive fields in one broadly readable profile table.
- Use masked display fields in normal UI screens. Only authorised workflows should decrypt necessary PII, and each access should be audit-logged.
- Model member eligibility as a timestamped, purpose-specific verification response. For example, a health partner should receive a minimal yes/no eligibility response, not medical history or a general Omang search.
- Keep benefit records versioned with a status (`confirmed`, `terms_to_verify`, `expired`, `under_review`), effective date, expiry date, internal owner and source.
- Use maker-checker approval for changes to payroll rules, partner rates, benefit eligibility and content publishing.
- Separate `requested`, `under_review`, `approved`, `declined`, `paid` and `closed` application states. Do not equate an enquiry with approval.
- Do not store passwords, raw API keys or partner client secrets in the member/profile JSON. Use a secrets manager in production.
- Treat all current salary amounts, deduction totals, optional family premiums, loan balances and savings balances in this pack as made-up UI examples. Validate the 1% subscription cap and all P70/P20/P39.50 payroll line labels with BOPEU before production.
